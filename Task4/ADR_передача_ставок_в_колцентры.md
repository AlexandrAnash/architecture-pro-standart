### **Решение**

Решение опирается на сервис ставок, созданный в MVP: он уже является единственным источником ставок в банке и уже публикует версию справочника в топик Kafka `deposit.rates`. Новых источников данных не создаётся, добавляются только два способа доставки.

**Кол-центр банка — онлайн через API.** В системе кол-центра добавляются два компонента: виджет актуальных ставок в карточке обращения и клиент API ставок, который ходит в сервис ставок через API Gateway и кеширует последний успешный ответ. Система кол-центра микросервисная, на Java Spring Boot, дорабатывается в рамках возможностей расширения платформы.

**Партнёрский кол-центр — файлом через SFTP.** Добавляется новый компонент депозитной платформы — **сервис публикации ставок**. Он подписан на топик `deposit.rates`, при изменении справочника собирает срез публичных ставок, формирует CSV-файл и манифест, считает контрольную сумму, подписывает и выкладывает в SFTP-каталог в демилитаризованной зоне. Партнёр подключается к каталогу по ключу и забирает файл. Дополнительно работает планировщик, который выкладывает файл не реже раза в сутки, даже если изменений не было.

Логика принятых решений и выбора технологий:

- **Два разных способа доставки.** Кол-центр банка внутри контура и может ходить в API — там данные отдаются онлайн. Партнёр заявил, что API-вызовы невозможны, ему остаётся файл. Попытка навязать партнёру API означала бы отсутствие решения вообще.
- **Источник один.** И виджет кол-центра, и файл партнёра берут данные из одного сервиса ставок. Отдельная копия справочника у партнёра дала бы второй источник истины — ровно ту проблему, которую устранял MVP.
- **Выгрузка по событию, а не только по расписанию.** Ставка меняется в течение дня, выгрузка раз в сутки означала бы вчерашние данные у партнёра. Планировщик оставлен страховкой: если событий не было, партнёр видит, что канал жив.
- **Манифест, версия и контрольная сумма.** Обратной связи от партнёра нет. Манифест позволяет ему проверить целостность и новизну файла, а банку — доказать, какие ставки и когда были переданы.
- **Наружу уходят только публичные базовые ставки.** Индивидуальные ставки и данные кредитного риска — внутренняя информация банка. Срез собирает отдельный компонент через публичный API, а не чтением базы.
- **В кол-центре кешируется последний успешный ответ.** Оператор не может ждать. Лучше показать вчерашнюю ставку с отметкой времени, чем пустой экран: оператор предупредит клиента, что условия подтверждает банк.
- **SFTP-каталог в демилитаризованной зоне.** Партнёру доступ только на чтение и только к своей папке, по ключу. Направление обмена одно: банк кладёт, партнёр забирает.

### **Альтернативы**

1. **Доступ партнёра к API ставок банка**
   - Один способ доставки для обоих кол-центров
   - Партнёр всегда видит актуальные данные, расхождений между каналами нет
   - Но партнёр заявил, что API-вызовы с его стороны невозможны, он готов принимать только файлы

2. **Автоматическая рассылка ставок по электронной почте**
   - Привычный для обеих сторон канал, менять процесс не нужно
   - Не требует SFTP-каталога и согласования с информационной безопасностью
   - Но нет контроля доставки, версионирования и целостности, а разбор вложения на стороне партнёра остаётся ручным

**Недостатки, ограничения, риски**

**Недостатки решения**

1. Партнёр всегда работает со срезом, а не с онлайн-данными. Между выгрузками ставка может измениться, и оператор партнёра назовёт устаревшее значение. Компенсируется меткой времени в файле и правилом озвучивать ставку с оговоркой, но полностью не устраняется.
2. Добавляется ещё один компонент депозитной платформы и новая точка на периметре — SFTP-каталог, который нужно сопровождать и контролировать.
3. Два канала доставки одних и тех же данных нужно тестировать и поддерживать раздельно.

**Ограничения**

1. Доработка системы кол-центра возможна только в рамках возможностей расширения платформы подрядчика. Если платформа не позволит добавить виджет в карточку обращения, потребуется отдельное окно, что ухудшит работу оператора.
2. Банк не управляет тем, как часто партнёр забирает файл и как быстро загружает его в свою систему. Фактическая задержка на стороне партнёра банку неизвестна.
3. Обратный канал отсутствует: партнёр не сообщает, какую версию применил. Банк видит только факт скачивания файла.
4. Индивидуальные ставки в партнёрский кол-центр не передаются в принципе, поэтому клиента с особыми условиями партнёр проконсультировать не сможет и должен переводить его в банк.

**Риски**

1. **Расхождение ставок между каналами.** Клиент может услышать разные значения в банке и у партнёра. Снижается сокращением интервала выгрузки и обязательной меткой времени, но требует регламента для операторов.
2. **Выход SFTP-каталога на периметр требует согласования с информационной безопасностью.** Работа может занять больше времени, чем разработка сервиса публикации. Согласование нужно начинать в первый месяц, до начала разработки.
3. **Ограничения платформы кол-центра выясняются только в ходе доработки.** Нужно провести техническую проверку возможности встроить виджет до планирования сроков.
4. **Рост нагрузки на сервис ставок от кол-центра.** Двести операторов банка обращаются к справочнику постоянно. Кеш в системе кол-центра и кеш в сервисе ставок обязательны, нагрузочное тестирование должно учитывать этот трафик.
5. **Утечка данных через выгрузку.** Ошибка в формировании среза может отправить наружу индивидуальные ставки. Снижается тем, что срез собирает отдельный компонент через публичный API, а не читает базу напрямую, плюс проверка состава полей в тестах.
