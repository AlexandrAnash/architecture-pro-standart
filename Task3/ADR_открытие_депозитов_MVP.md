### **Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| 1 | Доступность сервисов не ниже 99,9 %, режим работы 24/7 |
| 2 | При отказе одного ЦОД сервисы подачи заявки и просмотра ставок остаются доступны и выдерживают нагрузку |
| 3 | Онлайн-подача заявок не увеличивает нагрузку на базу данных АБС сверх управляемого предела |
| 4 | Заявка клиента не теряется при недоступности АБС или бэк-офиса |
| 5 | Отклик каналов на запрос ставок и подачу заявки измеряется миллисекундами, справочные данные отдаются из кеша |
| 6 | Новые компоненты масштабируются горизонтально, запросы распределяются между серверами и ЦОД |
| 7 | Трафик с чувствительными данными клиента шифруется на сайте и в интернет-банке |
| 8 | Сотрудники бэк-офиса депозитов и бэк-офиса кредитов не имеют доступа к данным друг друга |
| 9 | Изменение ставки фиксируется с указанием автора и времени |
| 10 | Повторная отправка заявки не создает дубль |
| 11 | Ядро интернет-банка не дорабатывается, доработки подрядчика не требуются |
| 12 | Используются технологии, по которым в банке есть экспертиза: Java Spring Boot, PostgreSQL, Kafka, React |
| 13 | Интерфейсы соответствуют системе дизайна компании и рассчитаны на клиентов старшего возраста |
| 14 | Решение развивается до целевого состояния без участия бэк-офиса без переписывания архитектуры |

### **Решение**

Диаграммы:

- [Диаграмма контекста](./C4_context_депозиты_MVP.png)
- [Диаграмма контейнеров](./C4_container_депозиты_MVP.png)

Создается отдельная **Депозитная платформа** — набор новых сервисов банка. Существующие системы почти не меняются: интернет-банк и АБС получают по одному новому компоненту, сайт и система кол-центра — только интеграцию.

Состав новых компонентов:

| Компонент | Технологии | Назначение |
|---|---|---|
| Сервис ставок | Java 17, Spring Boot, PostgreSQL | Единственный источник ставок: расчет, хранение, история изменений, публикация в Kafka, кеш в памяти |
| Сервис заявок на депозит | Java 17, Spring Boot, PostgreSQL | Прием заявок из каналов, идемпотентность, статусы, фиксация ставки |
| Сервис уведомлений и кодов | Java 17, Spring Boot | Одноразовые коды и СМС-уведомления через существующий СМС-шлюз |
| API Gateway | Spring Cloud Gateway | Точка входа для каналов: TLS, аутентификация, лимиты |
| Интерфейс управления ставками | React.js | Разные экраны для бэк-офиса депозитов и бэк-офиса кредитов |
| Kafka | Apache Kafka | Топики deposit.applications, deposit.status, deposit.rates |
| Адаптер АБС | Java 17, Spring Boot | Единственный компонент, работающий с АБС. Читает Kafka, ограничивает нагрузку |
| Депозитный модуль | React.js, SPA | Витрина ставок и подача заявки в интерфейсе интернет-банка, ядро не затрагивает |
| Интеграционный API АБС | PL/SQL, REST | Прием заявок и выдача статусов. Разрабатывает команда АБС |

Отказоустойчивость и масштабирование:

Новые сервисы разворачиваются в обоих ЦОД в режиме active-active, состояния не хранят, масштабируются горизонтально. Kafka — кластер с репликацией между ЦОД. АБС остаётся в основном ЦОД и вертикально масштабируемой. При отказе ЦОД просмотр ставок и подача заявки работают, накопленные заявки обрабатываются из топика после переключения.

### **Альтернативы**

1. **Реализация ставок и согласования в АБС**
   - Не требует новых систем, всё хранится в одном месте
   - Бэк-офис работает в привычном интерфейсе, обучение не нужно
   - Но база АБС уже перегружена и масштабируется только вертикально, а три онлайн-канала дали бы постоянный поток чтений

2. **Доработка монолита интернет-банка силами подрядчика**
   - Единый интерфейс без швов, новых компонентов не появляется
   - Не нужен отдельный контур эксплуатации: Kafka, шлюз, набор сервисов
   - Но сроки и стоимость определяет подрядчик, а платформа несовместима с Kafka, поэтому асинхронный обмен всё равно пришлось бы строить снаружи

**Недостатки, ограничения, риски**

**Недостатки**

1. Семь новых компонентов и новый контур эксплуатации: Kafka, API Gateway, сервисы. Нужны команда сопровождения и мониторинг, которых сейчас нет.
2. Депозитный сценарий и остальной интернет-банк — разные приложения. Единая система дизайна становится обязательной, а не желательной.
3. Заявка живет и в сервисе заявок, и в АБС. До обработки актуальное состояние знает только сервис заявок.

**Ограничения**

1. Ручная обработка в АБС сохраняется, время реакции определяется графиком сотрудников.
2. Нужна доработка АБС — интеграционный API.
3. Нужна доработка системы кол-центра для приема заявок с сайта
4. Использование старого стека технологий

**Риски**

1. **АБС остается узким местом.** Нужен лимит частоты вызовов и нагрузочное тестирование интеграционного API до запуска.
2. **Целевые показатели нагрузки не заданы.** Без числа клиентов и пика заявок конфигурацию не рассчитать, риск высокой нагрузки. 
3. **Зависимость от команды АБС и подрядчика кол-центра.** Их работы на критическом пути.
